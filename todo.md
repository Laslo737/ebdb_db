## Контекст проекта
Нужно сделать простого бота для Яндекс Мессенджера, который будет работать как удобная прослойка между пользователями и существующей базой / API.

Цель: упростить работу с филиалами и связанными сущностями, в первую очередь с контактами филиала.

## Проблема
Сейчас база и API неудобны для ручной работы:
- чтобы изменить / добавить / удалить контакт, нужно знать `id` филиала;
- чтобы узнать `id` филиала, приходится получать список филиалов и искать нужный филиал по косвенным полям;
- филиал содержит несколько связанных сущностей, например:
  - `iiko`
  - `contacts`
  - `location`
  - `metrics`
  - `banking_info`
  - `meta_info`
  - `dogovors`
- контакты филиала представлены отдельными сущностями, например:
  - `Партнер №1`
  - `Партнер №2`
  - `Управляющий`

## Идея решения
Сделать бота в Яндекс Мессенджере, который будет:
- принимать запросы от пользователя;
- искать филиал по удобным признакам;
- помогать выбрать нужный филиал, если найдено несколько вариантов;
- выполнять действия через API;
- возвращать понятный результат пользователю.

## Что обсуждали
Предварительно определили, что бот должен уметь:
- искать филиалы;
- показывать информацию по филиалу;
- показывать контакты филиала;
- добавлять контакт;
- изменять контакт;
- удалять контакт.

Потенциальные поля поиска филиала:
- `iiko.address_tt`
- `jur_lico`
- возможно `id`
- возможно `location.address`
- возможно `location.city`

Уточнение по поиску по `jur_lico`:
- поиск не должен зависеть от точного формата полного юр. лица;
- в запросе пользователь может писать только ФИО целиком или частично, например `Коваленко Ольга` или `Дмитриев Иван`;
- различия вида `ИП`, `Индивидуальный предприниматель` и другие префиксы не должны мешать поиску;
- если найдено несколько филиалов по одному ФИО / набору токенов, бот должен показать список найденных филиалов и предложить пользователю выбрать нужный кнопками.

## Подтвержденная информация по Yandex Messenger Bot API
Подтвержденные параметры интеграции:
- base URL: `https://botapi.messenger.yandex.net`;
- авторизация: заголовок `Authorization: OAuth <token>`;
- bot self info: `GET /bot/v1/self/get`;
- отправка текста: `POST /bot/v1/messages/sendText/`;
- updates / webhook / polling: `GET/POST /bot/v1/messages/getUpdates/`;
- настройка webhook: `POST /bot/v1/self/update/`;
- ограничение текста: до `6000` символов;
- можно отправлять сообщение по:
  - `chat_id`
  - `login`;
- поддерживается `thread_id`;
- для request correlation / idempotency-like поведения используется `payload_id`;
- webhook доставляется по семантике `at-least-once`, поэтому dedupe обязателен.

## ENV-переменные для Yandex Messenger
Основные env:
- `ENABLE_YANDEX=true` или `ENABLE_YANDEX_MESSENGER=true`

Основные переменные интеграции:
- `YANDEX_MESSENGER_KEY` — основной токен;
- `YANDEX_MESSANGER_KEY` — legacy alias, использовать только для совместимости;
- `YANDEX_WEBHOOK_SECRET` — optional secret для webhook;
- `YANDEX_BOT_ID` — scaffold-параметр;
- `YANDEX_API_BASE_URL` — если потребуется переопределить base URL;
- `YANDEX_AUTH_HEADER` — если потребуется переопределить имя auth header;
- `YANDEX_AUTH_SCHEME` — если потребуется переопределить схему, по умолчанию `OAuth`.

## Важные особенности webhook
Текущий рабочий подход из другого проекта:
- внутренний endpoint: `POST /api/channels/yandex/webhook`;
- secret может проверяться по headers:
  - `x-webhook-secret`
  - `x-channel-secret`
  - `x-bot-secret`;
- webhook лучше обрабатывать по схеме `fast-ack + async processing`;
- из-за короткого timeout у Yandex надо быстро отвечать `200 OK`;
- от повторной обработки нужен dedupe.

- в private reply target = `login`;

- non-text события нужно обрабатывать мягко, без падения.

## Контекст на будущее: смена партнера у филиала и юр. лица
Ниже зафиксированы выводы, которые были получены в ходе обсуждения и ручных проверок API, но пока не реализованы в боте как полноценный сценарий.

### Что подтверждено по API
- `GET /api/v1/partners/search/by-fio/{fio}`:
  - если партнер найден, API возвращает массив партнеров;
  - если не найден, API может вернуть объект вида `{ "detail": "Партнеры с ФИО ... не найдены" }`, а не пустой массив.
- `POST /api/v1/partners/`:
  - подтверждено, что партнера можно создать минимальным payload вида `{ "fio": "..." }`.
- `PATCH /api/v1/partners/filials/{filial_id}`:
  - подтверждено, что можно менять `partner_id`;
  - подтверждено, что можно отдельно менять `jur_lico`;
  - подтверждено, что можно одним запросом менять и `partner_id`, и `jur_lico`.

### Что выявлено по бизнес-логике
- `partner_id` филиала и `jur_lico` филиала — не одно и то же.
- Часто юридическое лицо и юридический партнер совпадают по человеку, но бывают кейсы, когда это разные сущности.
- В реальных данных возможен филиал, у которого:
  - `partner_id` указывает на одного партнера;
  - `jur_lico` содержит другое юридическое лицо;
  - контакт филиала типа `Партнер №1` при этом тоже является отдельной связанной сущностью.
- Поэтому автоматическая смена `partner_id` при изменении `jur_lico` опасна и пока сознательно не внедряется.

### Что уже известно про модель данных партнера
- У партнера есть как минимум:
  - карточка партнера (`fio`, `fio_2`, `jur_info`, `finance_info`, `meta_info` и т.д.);
  - отдельные `partner_contacts` / контакты партнера.
- На практике при создании нового партнера для полноценной записи в базе, скорее всего, нужен не только сам партнер, но и создание контакта партнера.
- По примеру из БД у контакта партнера используются поля:
  - `phone_1`, `phone_2`, `telegram`, `email`, `birthday`, `clothes_size` — юридический блок;
  - `phone_2_1`, `phone_2_2`, `telegram_2`, `email_2`, `birthday_2`, `clothes_size_2` — фактический блок;
  - `yandex_messenger_login`, `email_yandex`.

### Какой безопасный MVP выбран сейчас
- Пока реализован только простой сценарий `изменить юр лицо`:
  - бот показывает текущее `jur_lico` филиала;
  - просит ввести новое значение;
  - обновляет только поле `jur_lico` через `PATCH /api/v1/partners/filials/{filial_id}`.
- Комплексная смена партнера / юридического партнера отложена до отдельного этапа.
- После успешного поиска филиала бот теперь сразу показывает не только карточку филиала, но и список его контактов, чтобы пользователь видел контекст до перехода в отдельный пункт `контакты`.
- В сценарии `добавить контакт` для поля `contact_type` добавлены быстрые кнопки допустимых значений:
  - `Управляющий`
  - `Партнер №1`
  - `Партнер №2`
- В сценарии `добавить контакт` поле `email` явно подписано как личный email контакта.
- В сценарий `добавить контакт` добавлен шаг заполнения `yandex_messenger_login` с подсказкой, что это учетка Yandex Messenger, связанная с филиалом.

### Что продумать позже перед реализацией комплексного сценария
- Нужно ли менять только `jur_lico` или также:
  - контакт филиала `Партнер №1`;
  - `partner_id` филиала;
  - карточку партнера;
  - контакты партнера.
- Нужен отдельный пошаговый UX, который безопасно разделяет действия:
  - изменить только `jur_lico`;
  - найти существующего партнера;
  - создать нового партнера;
  - создать контакт партнера;
  - при необходимости отдельно подтвердить смену `partner_id`.

## Новая договоренность на следующий этап
Новый ближайший сценарий для реализации в боте: `изменить партнера` у филиала.

Ожидаемая логика сценария:
- бот показывает текущего партнера, который привязан к филиалу через `partner_id`;
- бот дополнительно показывает контакты этого партнера отдельным запросом в API (`GET /api/v1/partners/{partner_id}/contacts`);
- после ввода нового партнера бот сначала ищет уже существующих партнеров;
- поиск партнера должен быть устойчив к разному вводу и не зависеть от префиксов вида `ИП` / `индивидуальный предприниматель` и других вариаций записи ФИО;
- если найден один партнер, бот должен показать его карточку и контакты и предложить выбор: использовать найденного или создать нового;
- если найдено несколько партнеров / дублей, бот должен показать варианты с кнопками выбора (`1`, `2`, `3`, ...), а также опцию `Создать нового`;
- если партнер не найден, бот должен перейти к созданию нового партнера;
- создание нового партнера должно начинаться с ввода корректного ФИО;
- после создания партнера бот должен предложить создать контакт партнера и собрать минимум такие поля:
  - `phone_1`
  - `telegram`
  - `email`
  - `email_yandex`
  - `yandex_messenger_login`
- для необязательных полей пользователь может отвечать `нет` или `-`, чтобы оставить значение пустым;
- после выбора существующего партнера или создания нового бот должен обновлять `partner_id` филиала через `PATCH /api/v1/partners/filials/{filial_id}`.

## Новая договоренность: сценарий `создать филиал`
Подтверждена потребность добавить в бота отдельный пошаговый сценарий создания нового филиала с антидубль-проверками на каждом этапе.

Ожидаемые шаги сценария:
1. Выбор или создание партнера.
2. Выбор или создание территории.
3. Создание филиала.
4. Создание `iiko` для филиала.
5. Опциональное создание контактов филиала.

### Шаг 1. Партнер
- поиск партнера должен быть не только точным, а похожим / нормализованным;
- различия вида `ИП`, `Индивидуальный предприниматель`, `ООО` и другие префиксы не должны мешать поиску;
- если найден существующий партнер, бот показывает кандидатов и предлагает использовать одного из них;
- если подходящего партнера нет, бот создает нового;
- после создания нового партнера бот должен отдельно предложить: заполнять ли сейчас контакт партнера;
- создание контакта партнера не обязательно, его можно пропустить.

### Шаг 2. Территория
- использовать `GET /api/v1/territories/` для поиска существующих территорий;
- если находится подходящая территория, бот должен предложить использовать ее;
- если подходящей территории нет, бот должен создать новую через `POST /api/v1/territories/`;
- при создании новой территории использовать тип `Новая территория`;
- остальные поля новой территории по умолчанию:
  - `development_potential = 0`
  - `resale_territory = false`
  - `paushalniy = 0`

### Шаг 3. Создание филиала
- дубль филиала сначала проверяется по `iiko.address_tt`;
- если по `iiko.address_tt` найден существующий филиал, бот показывает его и не создает дубль молча;
- если по `iiko.address_tt` совпадений нет, дополнительно проверять по `jur_lico`;
- минимально обязательные и подтвержденные для сценария поля создания филиала:
  - `partner_id`
  - `date_open`
  - `jur_lico`
  - `territory_id`
  - `status`
  - `category` (опционально, можно пропустить)
  - `filial_type`
  - `vnutrenniy_priznak_uo`
- `partner_id` бот подставляет из выбранного / созданного партнера;
- по примеру реального филиала подтверждено, что в API используются русские значения enum, например:
  - `status = Открыт`
  - `filial_type = ФС`
  - `vnutrenniy_priznak_uo = РФ`
- `date_open` бот должен запрашивать у пользователя отдельным шагом;
- на шаге `date_open` должна быть быстрая кнопка с сегодняшней датой, чтобы пользователь мог выбрать ее без ручного ввода;
- статус филиала пользователь должен выбирать кнопками из вариантов:
  - `Запускается`
  - `Открыт`
  - `На стопе`
  - `Не передано в запуск`
  - `Закрыт`
  - `Отказ`
- `category` бот должен предлагать отдельным шагом через кнопки, но это поле можно пропустить;
- тип филиала пользователь должен выбирать кнопками из вариантов:
  - `РС`
  - `ФС`
- `vnutrenniy_priznak_uo` пользователь должен выбирать кнопками из вариантов:
  - `РФ`
  - `Казахстан`
  - `Беларусь`
  - `Расторгнутые`
  - `ТиЧ`
  - `Взыскание`

### Шаг 4. IIKO филиала
- использовать `GET /api/v1/partners/filials/{filial_id}/iiko` и `POST /api/v1/partners/filials/{filial_id}/iiko`;
- перед созданием филиала антидубль-проверка в первую очередь опирается на `iiko.address_tt`;
- после создания филиала `iiko` создается отдельным шагом;
- на шаге `iiko` пользователь вводит как минимум `address_tt`, остальные поля можно оставить на потом или задать дефолтами по согласованию.

### Шаг 5. Контакты филиала
- после создания филиала бот по очереди предлагает создать контакты филиала:
  - `Партнер №1` — юридический партнер;
  - `Партнер №2` — фактический партнер;
  - `Управляющий`;
- каждый из этих контактов можно пропустить;
- создание контактов филиала должно быть полностью опциональным и не блокировать завершение сценария создания филиала.
